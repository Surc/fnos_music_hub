# 从 fnos_music_ext 迁移到独立 Hub

2026-10-24 新增原生预览打包实现，应用 ID/包用户/组为 `fnos_music_hub`；配置和数据使用独立 `var/config`、`var/state`、`var/downloads`。停启/备份/失败回滚/卸载保留详见 [预览包说明](../packaging/fpk/README.md)。这是新应用独立安装流程，不自动读取或搬迁旧 ext；实际构建结果和 fnOS/J4125 验收另行记录。

当前已开始独立开发版实现，但没有运行用户数据迁移、修改旧应用或生成新的 FPK 安装包。旧仓库仍是已发布能力与原上游历史的载体。

## 运行迁移的前置条件

新 Hub 使用独立应用标识和数据目录，准确值在 FPK 实现时确定。先备份旧配置与数据，建立 schema 迁移版本和回退点；不直接复用旧数据库或把旧共享网易账号批量转为各用户账号。

用户映射用实例命名空间与可信 GUID；旧数据缺归属时进入待确认/受限状态，不默认归给管理员。平台账号逐用户重新绑定或通过明确可验证的迁移方式处理。

旧 ext、fnmusic-sync 与新注入组件不能同时抢占官方音乐 Socket。首次启用前检测所有者，安全停用旧接管者再启用新组件；验证官方应用重启、Hub 停用/卸载/升级均能恢复原服务。未完成冲突检测前不建议在生产 NAS 并行启用注入。

只启用独立歌单/下载前台时无需接管 Socket。身份与曲库通过单独适配路径验证，注入开关不成为登录前置条件。

## 迁移完成的判据

两个用户的列表/账号/下载/文件仍隔离；历史与收藏数量和归属可核对；歌曲来源映射没有被标题猜测覆盖；任务可恢复；原文件可播放；停用新应用后旧链路可按记录恢复。每一步都需实际执行证据，设计检查不能替代迁移验收。

schema 2→3 只新增 playlist_captures 表，schema 1 亦支持升级；已有 manifests/tasks 及幂等请求哈希不改写。停服务后备份 hub.sqlite3 与 vault.key 再升级。旧程序拒绝 schema 3，不能直接降级；恢复匹配旧版本备份后回退。读取中断可回读句柄并从第一页重新两轮验证，不恢复旧远端页。此为受控迁移检查，真实 NAS 升级/停启尚未签收。
