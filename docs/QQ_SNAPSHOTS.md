# QQ 完整歌单快照

更新：2026-10-23（Asia/Makassar / UTC+8）。开发实现；真实 QQ 平台、音桥/NAS 验收仍待执行。QQ 下载保持关闭。接口仍是 v0.1 草案。

## 完整性的含义

`GET /api/catalog/qq/playlists/{id}` 继续提供原分页预览，始终 `complete=false / integrity=page_only`。前台翻页结果不能拼接后自行宣称完整。

新增服务端读取流程固定 QQMusicApi 0.8.2 的 `get_detail(num=100, page=...)`，一个尝试只使用一个冻结账号授权与凭据快照。顺序完成两轮全量分页，只有以下条件同时满足才保存 `DownloadManifest` 并标记 `complete=true / integrity=double_read_verified`：

1. 每页有整数 `total_song_num`、`songlist_size`、100 项以内的 `songlist`，`hasmore` 必须是布尔或 0/1；缺字段、字符串布尔或提前终止均拒绝。
2. 来源歌单 ID / 指定 dirid 匹配；dirid=0 是来源默认目录参数，不据此要求响应也为 0。所有页的总数和整个 `dirinfo` 一致。目录元数据变化也保守地判定漂移。
3. 每页长度等于 `min(100, total - offset)`，最后一页明确 `hasmore=false`，累计项数恰好等于总数；0 项歌单也要读取两次确认。
4. 第二轮每一页的原始有序条目、目录元数据、总数及结束标记的 SHA256 与第一轮相同。包括同总数增删/替换、重排和未知条目变成另一未知条目；不只比较第一页或规范化后的标题。
5. 每次平台调用前后重新验证账号引用、绑定代次、凭据修订和原生摘要；每页检查 Hub 会话未被注销，发布前再次向音桥验证身份并重验 QQ 授权。
6. 最终清单满足原有 1000 项 / 512 KiB 上限，清单和完成状态在一个 SQLite 事务中提交成功。

**两轮一致是观测验证，不是 QQ 的原子快照保证。** 固定 SDK/接口没有已验证的不可变版本令牌，因此 `source.version=null`、`source.verification.atomic=false`，明确记录观察开始/完成时间和页指纹。无法检测两次观察之间变化后恢复（ABA）、持续返回相同旧缓存、服务端稳定地错误切页等不可观测情况；也不保证最后一次读取后远端不变化。需要严格的单一时刻版本时，必须取得并验证上游版本/原子导出协议，不能把当前 complete 单独解释为该保证。

`complete=true` 仅表示本适配器的两轮全量观测规则全部通过且本地清单完整不可变；不表示可下载、会员资格、所有歌曲可用或真实平台已验收。整个 `dirinfo` 和原始条目参与比较可能因无关动态字段而保守失败，真实平台需验证后再有证据地收窄比较字段，不能为提高成功率忽略漂移。

## 保序、未知条目和不可变性

复用 `TrackRef`、`make_manifest()` 和 `manifests` 表。每个出现位置独立产生 `occurrence_id`，`position` 从 0 开始；同曲跨页重复或整页合法重复都保留，不做 ID 去重。未知项的 `song.track=null`，不减少总数。

每项保存原始条目的 `source_hash`；未知项另保存白名单标量 `id/mid/title/name/interval` 的原始占位元数据（字符串最多 512 字符）。任意扩展对象、Cookie、签名 URL、令牌不复制到数据库或浏览器。原始完整 JSON 只在内存中参与比较；不能称为原始响应的无损归档。

清单包含 owner、来源歌单、账号引用/绑定代次/凭据修订、固定 SDK SHA、适配器版本、观察区间、source_total、fetched_count、有序条目和内容哈希。哈希沿用 `hub.domain.canonical`：UTF-8 JSON、键排序、无额外空白、不转义中文；对除 `content_hash` 外的整个清单取 SHA256，包含时间和 occurrence ID。因此它验证这份不可变清单，不用作不同抓取之间的歌曲集合去重键。

已经保存的快照属于原飞牛用户，后续远端修改、刷新凭据、解绑或重启不会改写它；作为显式导入的本地数据可继续按 owner 读取。解绑禁止在途/后续远端读取，不隐式删除历史导入。另一个用户及管理员普通身份不能读取或恢复该快照。

## 请求、失败与恢复

| 方法 / 路径 | 行为 |
| --- | --- |
| `POST /api/catalog/qq/playlists/{id}/snapshots?dirid=...` | 需要 CSRF / Origin 和 `Idempotency-Key`；持久化 pending 句柄并返回 201，不开始平台读取；同 owner/键/歌单/账号关联重放返回原记录，异内容 409 |
| `POST /api/playlist-captures/{id}/run` | 显式开始/从头重试；已完成直接返回原结果，同用户已有读取则 409，不排第二个后台任务 |
| `GET /api/playlist-captures/{id}` | 本用户状态、轮次、已读取数量、错误、retry_at 与成功后的 manifest_id；不返回任何半成品曲目 |
| `GET /api/catalog/qq/playlists/{id}/snapshots?dirid=...` | 本用户该来源最近 20 条请求，用于丢响应、页面刷新或重启后找回句柄；不是完整历史导出 |
| `GET /api/manifests/{id}` | 按 owner 读取完整远端歌单清单；显式选曲下载清单不由此接口暴露内部 engine_song |

未完成的读取记录与不可变清单分别存储。状态为 `pending → reading → complete/incomplete`，成功才有 manifest_id；失败不缓存任何部分曲目，不会影响原分页浏览/收藏缓存。网络/契约/漂移/容量错误返回 HTTP 200 的 incomplete 记录及 `error.code/message`；平台账号失效、绑定变化、会话撤销仍返回原 409/401 并保存未完成状态。运行冲突和限流等待尚未结束为 409/429。非 2xx 不回传凭据或原始上游错误。

- 单页最多 30 秒，一个完整尝试最多 120 秒、最多 20 次详情读取（1000 项、两轮）；SDK 每次内部登录检查另计。超过 1000 项、512 KiB 或来源单页 512 KiB 明确失败，不截断当作成功。
- 不自动重试平台请求。超时/断网/取消/漂移后由用户显式重试，两轮都从第一页开始，旧页不参与新清单。它是安全恢复句柄，不是断点拼接旧远端数据。
- 限流后等待至少 30 秒；绝对 Unix 秒 `retry_at` 持久化，按 owner 检查所有请求中的最大等待时间。重启或新建另一个句柄都不能绕过；其他用户不被此账号的冷却阻塞。没有猜测来源未提供的 Retry-After。
- 同账号凭据修订在尝试中变化会中止；下一次显式重试可以取得新修订并从头验证，绑定代次不变。解绑/重绑/换号使旧请求无法再执行，需新请求。
- 进程崩溃留下的 reading 记录在回读时显示 interrupted/incomplete；恢复时重新取得当前合法授权，从第一页重新两轮验证。完成清单与状态同一事务发布，不存在已完成却没有清单的正常中间状态。
- `/run` 是有界请求内操作，没有新增持久队列/常驻进程。反向代理可超时，客户端应先 GET 回读状态；不能把丢响应当成“未保存”反复创建请求。服务重启不自动使用旧会话在后台继续私人读取。

数据库 schema 2→3 只增加 `playlist_captures` 表；schema 1 可逐步升级。升级前停服务并一起备份数据库与 vault.key；旧程序不能降级读取 schema 3，回退须恢复匹配备份。原 manifests/tasks 记录及下载幂等哈希不重写。

## 前台与下载兼容

歌单详情仍是每页 100 项的实时预览，保留原翻页/本地收藏；新增“生成完整快照”“回读已保存快照”“从头重试快照”和只读曲目明细。旋转不重新读取/提交；退出和账号切换丢弃迟到响应。快照动作不更改现有选曲或下载确认草稿，也不发出 `/api/tasks`。

QQ 的下载按钮保持禁用，后端 `/api/tasks` 对远端 QQ 清单（包括空歌单和含 unknown 的歌单）明确返回 unsupported。已有酷我显式清单、任务副本、同键重放、冲突和恢复流程保留。来源快照成功绝不能作为开放 QQ 下载的依据。
